# ADR 0016: 個人情報を持たない端末内自動登録品質集計

## Status

Accepted

集計形式、過去月表示、権限制御、匿名レポートはADR 0017で拡張する。レシート内容を保存せず端末内だけで評価する本ADRの原則は継続する。

## Context

ADR 0014でHigh confidenceの単体レシートを自動保存し、ADR 0015でLowまたはuncertainを後から確認できる端末内Inboxを追加した。管理者と家族の実機で、自動保存、Undo、要確認Inboxの復元・保存・破棄が動作することを確認した。

次にConfidence閾値や一括読み取りを変更するには、自動保存によって実際に操作が減っているか、誤った総額をHighとしていないかを評価する必要がある。一方、レシート画像、OCR全文、店舗、日付、金額、品目、利用者識別子を分析サービスや運用ログへ送ることは、現在の家庭内利用とプライバシー方針に対して過剰である。

## Decision

- 自動登録の品質は、撮影したブラウザの `localStorage` に集計値だけを保存して評価する。
- active household IDでscopeし、同じブラウザでも別家計簿の集計を表示しない。クラウド家計簿がない場合は端末ローカルscopeを使う。
- 1レシート単位の履歴は保存せず、月別カウンタへ直ちに加算する。
- 月別集計は最新12か月だけ保持する。
- Firestore、IndexedDBの支出、要確認Inbox、バックアップ、CSV、Google Sheets、Cloud Run、外部Analytics、運用ログへ集計を送らない。
- 集計は通常画面へ追加せず、既存の折りたたまれた管理者メニュー内だけに表示する。
- 管理者は現在のscopeの端末内集計を明示的に消去できる。データ初期化時にも消去する。

## Metrics

保存する値は次に限定する。

- 読み取り処理件数
- 実際に確認画面を省略して自動登録した件数
- 要確認へ送った件数
- 要確認となった説明可能な理由コード別件数
- 自動登録直後の10秒以内に「元に戻す」を成功した件数
- 要確認から保存した件数
- 要確認保存時に、初期の総額候補から総額を変更した件数
- 要確認を明示的に破棄した件数

指標は次のように定義する。

- 自動登録率 = 自動登録件数 / 読み取り処理件数
- Undo率 = 自動登録直後の取り消し件数 / 自動登録件数
- 要確認時の総額修正率 = 要確認保存時の総額変更件数 / 要確認から保存した件数
- 複数枚読み取りは、画像単位自動保存を実装するまでは実際の動線どおり `batch_flow` 理由の要確認として数える。

支出一覧で後から行った編集は、初期版の総額修正率へ含めない。自動保存済み支出との永続的な対応付けには支出IDまたは判定履歴の保持が必要になるためである。

## Data Model

`localStorage` key `cakb-receipt-quality-metrics-v1` に、version、household scope、月別カウンタ、理由コード別カウンタを保持する。

次は保存しない。

- レシート画像、画像名、OCR全文、座標block
- 店舗名、日付、総額、品目、カテゴリ、メモ
- 支出ID、要確認ID
- Firebase UID、メールアドレス、表示名

`Expense`、Firestore、IndexedDBのschemaは変更しないためmigrationは不要である。保存値が壊れている場合や未対応versionの場合は空の集計として扱い、レシート登録を失敗させない。

## UX

- 撮影、自動保存、要確認、Undoの通常操作を増やさない。
- 管理者向け表示では、実装用語や不透明なスコアではなく、件数、割合、確認理由を示す。
- 「この端末のみ」「店舗名、金額、画像、読み取った文字は記録しない」と明示する。
- 集計の保存失敗は支出登録や確認保存をブロックしない。

## Security And Privacy

- 集計処理へレシート内容や支出オブジェクトを渡さず、決定結果、理由コード、総額を変更したかというbooleanだけを渡す。
- household scopeは端末内表示の分離にだけ使い、外部へ送信しない。
- 外部Analytics、クラウド集計、商用利用向け横断分析を追加する場合は、収集目的、同意、保持期間、削除、認可、匿名化を新しいADRで決定する。
- 同じhouseholdの利用者が同じブラウザprofileを共用する場合は集計も共有する。

## Alternatives Considered

- Firestoreへレシート単位の判定結果を保存する: 端末横断集計はできるが、支出との関連付け、家族共有、保持期間、Rules、同意が必要になるため採用しない。
- Google Analyticsなど外部サービスへeventを送る: 運用は容易だが、現在の家庭内評価には過剰であり、送信範囲と同意が未設計のため採用しない。
- 支出にConfidenceや自動保存フラグを追加する: 後編集を追跡できるが、Firestoreとバックアップのschema変更になり、支出の正本へ処理メタデータを混ぜるため採用しない。
- 集計を実装せず実機の感想だけで閾値を変える: 誤った総額をHighにするリスクを比較できないため採用しない。

## Consequences

- レシート内容を収集せず、自動保存による操作削減と要確認原因を月単位で確認できる。
- 家族の別端末の集計は合算されず、端末ごとに確認する必要がある。
- 集計は厳密な監査ログではなく、複数tabの同時更新やブラウザデータ削除で欠落する可能性がある。
- Confidence閾値を変更する前に、匿名fixtureの回帰結果と端末内集計を合わせて判断できる。
