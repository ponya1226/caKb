# ADR 0014: 撮影中心のConfidence判定付き自動保存

## Status

Accepted

## Context

caKbはGoogle Visionとレシート解析の改善により、実レシートから日付、店舗、総額、品目を取得できるようになった。一方、ADR 0011までの通常フローは、すべてのレシートで候補選択、カテゴリ選択、確認、保存を利用者へ要求する。「家計簿を記録するための操作を限りなくゼロにする」という価値に対し、この全件確認が最大の操作負担になっている。

ただし、OCRと決定論的な候補抽出には誤認識が残る。特に残高、預かり金、釣銭、税額を支出総額として自動保存する失敗は、確認操作が残ることより重大である。すべてを無条件に保存することは採用できない。

## Decision

caKbの中心コンセプトを「家計簿をつけなくていい家計簿」とし、通常利用を撮影中心へ変更する。

- High confidenceの単体レシートは確認画面を表示せず、自動保存する。
- Lowまたはuncertain confidenceの結果だけを「要確認」として既存確認画面へ送る。
- 自動保存後は短時間の「元に戻す」を提供する。
- 支出の正本として日付、総額、店舗、カテゴリを優先する。品目明細はADR 0008どおり付加情報とし、品目欠落だけでは要確認にしない。
- カテゴリは店舗別カテゴリルール、同一・類似店舗の履歴の順で解決する。初期実装でどちらもない店舗は要確認とする。
- 複数枚の完全自動保存、永続的な要確認Inbox、AI分析はこの最初の縦切りに含めない。

この決定は、ADR 0011の「OCR後は保存前に必ず利用者が確認・修正する」という部分を置き換える。Google Vision固定、画像全体の送信、失敗時の再試行・手入力方針は継続する。

## Confidence-based Auto Save

Confidence判定は説明可能な決定論的ルールとして `receiptParser.ts` の出力後に実行する。単一の不透明な0から100のスコアだけでは判定しない。

初期判定は次の信号を返す。

- `ocrSucceeded`
- `totalResolved`
- `dateResolved`
- `merchantResolved`
- `categoryResolved`
- `conflictingAmounts`
- `conflictingMerchants`
- `suspiciousBalanceCandidate`
- `lineItemConsistency`

自動保存には、OCR成功、強く一意な現実的総額、妥当な日付、明確な店舗、ルールまたは履歴によるカテゴリ解決が必要である。競合する強い金額候補または別額の残高候補がある場合は自動保存しない。判定理由はコードと利用者向け文言を持ち、確認画面で表示できるようにする。

誤った総額をHigh confidenceとすることを最重要failureとして扱い、閾値緩和より匿名fixtureによる回帰検証を優先する。

## Exception Review

- 要確認結果は既存のOCR確認画面へ送り、日付、店舗、総額、カテゴリ、メモ、品目を修正して保存できるようにする。
- 要確認ドラフトの再読み込み後保持はADR 0015の端末内一時Inboxに従う。
- 確認時に店舗カテゴリルールを保存すると、同一・類似店舗の次回読み取りを自動化できる。
- 再読み取り後も確認画面に入った結果は自動保存せず、利用者が保存する。

## UX Principles

- 通常フローは「ホームでレシートを撮る、撮影する、登録完了」とする。
- 候補選択、カテゴリ選択、確認、保存をHigh confidenceの通常フローへ表示しない。
- 確認画面は削除せず、例外処理に限定する。
- ホームは撮影を最優先操作とし、管理、共有、出力機能を主操作にしない。
- 操作や設定を増やす変更は、記録負担を減らすかを判断基準にする。

## Security And Privacy

- Google Visionは自前Proxy経由だけで利用し、Firebase ID tokenとactive household membershipを検証する。
- レシート画像をProxyへ永続保存せず、画像base64、OCR全文、支出をログへ出さない。
- 外部送信の事実は撮影画面で明示するが、毎回の追加確認クリックは要求しない。
- secret、API key、token、service account keyをrepositoryへ保存しない。
- WIF/OIDCの鍵なしdeploy、Firestore Rulesのhousehold分離、production deploy gateを維持する。
- UX簡略化を理由に認可、外部送信説明、利用量制限を削除しない。

## Data Model

Confidence判定と理由は `ReceiptDraft` の一時状態として扱う。`Expense`、IndexedDB、Firestoreの保存schemaは変更しないためmigrationは不要である。自動保存済み支出の `source` は既存互換の `receipt` を維持する。

## Alternatives Considered

- 全件確認を継続する: 誤保存を抑えられるが、中心価値である操作削減を実現できない。
- OCR成功時に無条件で自動保存する: 操作は最小だが、残高や競合金額の誤保存を防げない。
- 機械学習またはLLMで判定する: 将来の比較余地はあるが、説明可能性、コスト、個人情報、評価データの準備が不足しているため初期採用しない。
- 品目合計の一致を必須にする: 税、割引、OCR欠落で正しい総額まで要確認になるため採用しない。

## Consequences

- 学習済み店舗の通常レシートでは、撮影後の確認と保存操作が不要になる。
- 未知店舗や曖昧なレシートでは確認操作が残る。
- 保守的な初期閾値により自動保存率は限定されるが、回帰fixtureを増やして安全に調整できる。
- 自動保存後のUndoは既存Repository削除を使う。ローカル画像保存ONの場合は関連画像も削除する。
- 一括撮影のConfidence適用は後続タスクになる。

## Follow-up

- 要確認件数と理由の計測方法を、個人情報を送らない形で検討する。
- ADR 0015の端末内Inboxを実機で確認し、端末間共有が必要か評価する。
- 単体で安全性を確認した後、一括撮影へ画像単位の判定と自動保存を拡張する。
- 自動保存率、Undo率、総額修正率を基に閾値を調整する。
- Step Aの安定後に、支出増加要因や月末予測を含むStep Bへ進む。自然言語質問のStep Cは別判断とする。
