# ADR 0021: 品目取得根拠による自動保存ゲート

Date: 2026-08-15

## Status

Accepted

## Context

ADR 0020では、取得済み品目の合計が支払総額、または印字税額加算後の支払総額と完全一致する場合だけ品目整合性を `consistent` とした。しかし `receiptParser.ts` には、OCRで金額を対応付けられなかった商品が1件だけ残った場合に、小計と他品目の差額をその商品の金額として補完する処理がある。

この補完値が偶然または構造上小計と一致すると、v2は取得根拠を区別できずHigh confidenceとして自動保存できた。また、商品名または金額だけの行が複数連続した場合は、印字順による対応付けが正しいとは限らない。算術一致だけでは品目明細の信頼性を説明できない。

## Decision

- `ReceiptLineItemCandidate` に任意の `extractionMethod` を追加し、次の取得方式を区別する。
  - `same_line`: 商品名と金額を同じOCR行から取得
  - `name_before_amount`: 商品名の直後にある金額行を対応付け
  - `amount_before_name`: 金額の直後にある商品名行を対応付け
  - `discount_pair`: 割引表示と割引額を対応付け
  - `subtotal_residual`: 小計と他品目の差額から補完
  - `single_item_total`: 印字点数が1点の領収範囲から商品名と総額を限定補完
  - `ambiguous_pair`: 複数の商品名または金額が待機中で、印字順だけで対応付け
- `subtotal_residual` を含む場合は `inferredLineItems`、`ambiguous_pair` を含む場合は `ambiguousLineItems` としてConfidence根拠へ出す。
- 品目合計が算術的に一致していても、上記どちらかを含む場合はblocking理由として要確認へ送る。
- `single_item_total` は、印字点数が1点で総額が独立に解決済みの場合に限る既存補完であり、品目が0件の場合を一律に要確認にしないADR 0020の方針を維持するため、今回のblocking対象にはしない。
- 判定ルールversionを `receipt-confidence-v3` とし、端末内品質集計でv1、v2と分離する。
- 今後の品目抽出修正は、候補へ取得方式を付け、算術一致だけで信頼性を決めない。

## Data Model

変更対象は読み取り中および要確認Inbox内の一時型だけである。`Expense`、Firestore、CSV、バックアップ、Google Sheetsのschemaは変更しない。`extractionMethod` と新しいConfidence信号は任意フィールドとし、v2以前の要確認データをそのまま復元できる。IndexedDB version変更は不要である。

## UX

- 直接取得または一意な前後行対応で整合する通常レシートには操作を追加しない。
- 小計差分補完時は「小計から推定した品目を確認してください」と表示する。
- 複数行の対応が曖昧な場合は「品目と金額の対応を確認してください」と表示する。
- 既存の確認画面で品目を修正して保存できる。推定結果を無条件に破棄せず、修正候補として提示する。

## Alternatives Considered

- 算術一致だけを継続する: 誤った品目対応でもHighになり得るため不採用。
- 小計差分補完を削除する: 修正候補として有用で、確認画面の入力負担を減らせるため削除しない。
- 前後行結合をすべて要確認にする: Google Visionの自然な改行でも確認が増えすぎるため、一意な対応は継続する。
- 店舗別の例外だけ追加する: 同じ構造問題が別店舗でも再発し、取得根拠を説明できないため主方式にはしない。

## Consequences

- v3ではv2より要確認率が上がる可能性があるが、危険な補完と曖昧対応を理由別に計測できる。
- 推定候補は確認画面に残るため、利用者はゼロから入力せず修正できる。
- レシート個別の正規表現追加より、取得方式とレイアウト構造を基準に改善できる。
- POS形式別プロファイルや正解fixture評価へ進む際に、どの取得経路が失敗したか追跡できる。
